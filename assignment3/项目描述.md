## 第 0 部分：框架

### 两种容器

主 Agent 在 **Agent 容器**中运行。该容器根据课程提供的 `dispatcher/agent.Dockerfile` 构建，并挂载你的 `src/`。主 Agent 循环从一开始就在此容器中启动；记忆、子 Agent 以及其他功能也都应放在该容器中。

`starter_code` 文件夹以只读方式挂载到 `/madsOpt`。Agent 只能写入其中的两个位置：`.tasks/`（工作目录）和 `madsOpt_logs/`（日志目录）。其他需要写入的内容，例如临时文件和缓存，应放在容器中的其他位置，例如 `/tmp`。

每个任务都在**独立的任务容器**中运行，容器由该任务自己的镜像构建。镜像中包含检出到任务起始提交的仓库，以及任务所需的工具链和测试依赖。Agent 读取和修改的代码就在这个容器中。有些 Go 任务需要在修复时添加模块。这些任务的容器预先准备了模块缓存，并设置 `GOPROXY=off`，因此 `go get <module>@<version>` 和 `go mod tidy` 可以离线执行。要查看可用的模块版本，运行 `ls $(go env GOMODCACHE)/cache/download/<module>/@v/`。`evaluation_scripts/prepare_images.sh` 会构建这些镜像，使任务能够离线求解。

Agent 通过评测设施的调度器（dispatcher）启动任务、生成补丁并进行评测。这两类容器都不能直接访问互联网：Agent 容器唯一的外部访问通道是通往课程 API 的出口代理，`CS2680_BASE_URL` 指向该代理；任务容器没有任何互联网访问通道。

### Agent 如何访问任务

当 Agent 请求一个任务时，调度器会启动任务容器，等待其就绪，然后向 Agent 返回一个字典，其中包含任务规格和访问容器所需的信息：

```text
problem_statement, requirements, interface   # 问题描述及其规格要求
task                                         # 任务索引 k
sandbox_url                                  # http://<container>:8000
workdir                                      # 容器中的仓库路径，例如 /app
```

任务容器中运行着一个小型 HTTP 服务器（`src/sandbox_server.py`），提供四个路由：`/health`、`/exec`（在仓库中执行 shell 命令，返回标准输出、标准错误和退出码）、`/read`（读取文件）以及 `/write`（写入文件）。Agent 通过普通 HTTP POST 请求与其通信。

`src/sandbox.py` 将这些接口封装为 `Sandbox(url, workdir)`，提供 `exec`、`read_text` 和 `write_text` 方法。Agent 对仓库的所有操作都应通过这些方法进行。你可以根据需要增加路由，以支持新工具、子 Agent 等功能。不要通过本地 `open()` 或 `subprocess` 操作仓库：这些操作发生在 Agent 容器中，而仓库并不在该容器内。

### 接受评测并决定下一步

当 Agent 认为任务已经解决时，它会生成补丁并请求评测设施评分：

```python
dispatcher.extract_patch(k)        # 将任务容器中的 git diff 写入该任务的补丁目录
                                   # 也可以使用 dispatcher.submit_patch(k, text) 提交自己生成的补丁
ev = dispatcher.evaluate(k)        # -> {"tests_failed": F, "tests_total": T, "attempt": a}
```

评测设施会将补丁复制到从任务镜像创建的全新环境中。该环境具有相同的预热 Go 模块缓存，且没有网络连接。评测设施会应用任务的隐藏测试并运行，然后把测试总数和失败数返回给 Agent。之后，Agent 可以选择：

```python
dispatcher.continue_task(k)   # 继续工作：保留任务容器及已有修改，删除已提交的补丁。
                              # 生成新补丁后，可以再次调用 evaluate(k)。
dispatcher.done(k, reason, iterations)
                              # 结束任务：以最后一次评测作为最终结果。
                              # 如果补丁已提交但尚未评测，现在会进行评测；没有补丁则计为失败。
                              # 任务容器和补丁目录将被删除。
```

### 调度器强制执行的规则

- **最多同时存在 5 个进行中的任务。** 已打开 5 个任务时，`next_task()` 会抛出 `DispatcherError`；没有剩余任务时返回 `None`。
- **每个任务同一时间只能有一次评测尝试。** 任务 k 的评测尚未结束时，对该任务调用 `continue_task(k)`、`evaluate(k)` 或 `done(k)` 都会被拒绝。
- **单次评测限时 35 分钟。** 如果测试套件卡住，则该套件的所有测试均计为失败。
- **整轮运行限时 4 小时。** 从 Agent 打开第一个任务时开始计时。4 小时后，本轮运行停止：Agent 下一次调用调度器时会收到 `DispatcherShutdown`；所有仍在进行中的任务都会按照此时调用了 `done(k)` 的方式结束（采用最后一次评测结果；已提交但尚未评测的补丁会进行评测；没有补丁则计为失败）；从未打开的任务计为失败。已经开始的评测仍会执行完毕。

### 入口

```python
class Agent:
    def __init__(self, dispatcher): ...
    def run(self): ...
```

运行器创建 `Agent(dispatcher)` 并调用 `run()`。之后的流程由你决定：同时保持多少个任务处于打开状态，是否并行处理，何时评测，是否在失败任务上再尝试一次或转向其他任务，以及将哪些信息从一个任务带到下一个任务。

`src/agentic_loop.py` 中的初始 `Agent` 仅演示这些调用。它按顺序逐个领取任务，不尝试修复问题，因此在你实现自己的 Agent 之前，每个任务都会失败。

通过 `dispatcher.logger(k)` 记录模型调用和工具调用。排行榜会从这些轨迹日志中读取你的交互轮数。

### 运行方法

**步骤 0：前置条件。** Linux x86_64；Docker；`git`；带有 `pip` 的 `python3`（3.10 或更新版本）；约 15 GB 的可用磁盘空间，用于存放镜像。如果本地机器上遇到困难，可以使用 [CloudLab](https://cs2680.com/computing/cloudlab) 或 [AWS](https://cs2680.com/computing/aws) 机器。

```bash
# 仅在尚未安装 Docker 时执行：
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER
newgrp docker            # 或退出登录后重新登录
docker run hello-world   # 检查 Docker 是否正常工作

# 仅在 python3 没有 pip 时执行（出现 "No module named pip"）：
sudo apt update
sudo apt install python3-pip
```

**步骤 1：准备镜像。**

```bash
# 在共享课程仓库根目录运行：
cd assignment3/starter_code
bash evaluation_scripts/prepare_images.sh
```

该脚本会获取任务数据（固定提交版本的 SWE-bench Pro），为任务容器安装便携式 Python，下载 openai 的 wheel 包，拉取每个任务的镜像，构建 Agent 镜像，并为每个需要额外依赖包的 Go 任务构建预热镜像。构建成功后，最后会输出 `== all images present`。

**步骤 2：设置环境变量并测试。**

```bash
export CS2680_API_KEY=...
export CS2680_MODEL_EXPERT=expert        # Expert：能力最强；每百万 token：输入 $2.00，缓存输入 $0.10，输出 $10.00
export CS2680_MODEL_STANDARD=standard    # Standard：每百万 token：输入 $0.08，缓存输入 $0.004，输出 $0.28
export CS2680_MODEL_STARTER=starter      # Starter：最便宜；每百万 token：输入 $0.01，缓存输入 $0.0005，输出 $0.04
python3 evaluation_scripts/run_all.py --limit 0
```

`run_all.py` 会把所有 `CS2680_*` 环境变量传入 Agent 容器，并将 `CS2680_BASE_URL` 设置为出口代理地址，这是 Agent 访问课程 API 的唯一通道。Agent 应通过 `os.environ` 读取这些配置，绝不要硬编码 API URL。在同一轮运行中，Agent 可以使用这三个模型中的任意一个或多个，数量不限。

该命令会启动 Agent 容器和代理，检查网络规则（课程 API 可达，其他外部访问被阻断），启动每个任务容器并执行健康检查，然后停止，不实际执行 Agent 的任务求解流程。请确认输出包含 `EGRESS OK`，以及每个任务对应的 `preflight k: ... ok`。

第一次在终端运行 `run_all.py` 时，程序会要求你用拉丁字母填写名和姓，并保存到 `dispatcher/student_name.json`。之后，本轮运行的每次课程 API 请求都会携带会话 ID，格式为 `<First>_<Last>_<UTC start time>`，例如 `Jane_Doe_20261006T172408Z`。该 ID 由出口代理添加，运行时会打印出来，并保存到 `run_logs/session_id`。如果在没有交互终端的情况下运行（例如使用 `nohup`），请先填写该文件，否则程序会在启动任何内容之前退出。

**步骤 3：运行。**

```bash
python3 evaluation_scripts/run_all.py
```

运行进度写入 `run_logs/sequence.log`。运行结束后，`starter_code` 中会生成 `run_all_results.md`（例如 `3/5 passed`）、`pro_eval/`（各任务的评分输出）、`model_patch_<k>.diff` 和 `madsOpt_logs/<k>/run.jsonl`（Agent 的轨迹日志）。初始 Agent 只是一个骨架，不会修复任何问题，因此预期结果为 `0/5 passed`。

下一次运行前，请将上一次运行的输出归档到其他文件夹。

## 第 2 部分：排行榜提交

排行榜会在评测任务集上评测你的 `src/`，使用与初始代码相同的 `dispatcher/`、`madsOpt.py` 和 `evaluation_scripts/`。你上传的内容中，只有 `src/` 会被提取使用。排行榜地址：[https://leaderboard.cs2680.com/](https://leaderboard.cs2680.com/)。

**步骤 1：登录并修改密码。** 在排行榜页面，使用与你的 Canvas 账户关联的哈佛邮箱登录。初始密码为 `Cs2680-<你的 8 位学号>`，与 API 账户的初始登录凭据相同。登录后点击你的姓名，在下拉菜单中选择 `Change Password`。

**步骤 2：查看排行榜。** 登录后，`Leaderboard` 页面显示前 10 名学生，每位学生以其最佳提交代表；下方显示你自己的最佳提交及排名。每次评测完成后，排行榜都会立即更新。

**步骤 3：提交。** 在 Submit 页面上传 `src/` 文件夹的 zip 压缩包，并选择本轮最多评测多少个任务。本轮会使用评测集中的前 *k* 个任务；如果该字段留空，则使用全部任务。

**步骤 4：提交的衡量指标。** 每次提交都根据以下三个指标进行评估：

- 解决的任务数。
- 每个成功任务的费用：本轮运行中课程 API 账户的实际扣费，除以解决的任务数。
- 每个成功任务的耗时：从打开第一个任务到结束最后一个任务的端到端实际耗时（按宿主机时钟计量），除以解决的任务数。

**步骤 5：历史提交、取消和每日预算。** Past submissions 页面列出正在进行和过去的提交。同一时间最多只能有一个提交处于排队或评测状态，该提交会显示 **Cancel** 按钮。每位学生每天有 **30 美元**的排行榜评测预算，单次提交上限为 **10 美元**。如果评测达到任一上限，就会停止，并将截至该时刻已经完成的工作记录为本次提交结果。

- 取消仍在**排队**的提交，会将其从队列中移除，不产生费用。
- 取消**正在评测**的提交，会停止运行。已经产生的费用将从当天的 30 美元预算中扣除，提交结果则记录取消时的三个指标。

**步骤 6：Skyline（帕累托分层）排名。** 每位学生按其最佳提交排名。

- 解决了**至少 7 个任务**的最佳提交，会根据三个指标进行 skyline 分层。如果一个提交在三个指标上都不差于另一个提交，并且至少有一个指标更好，则前者支配后者。所有不被其他提交支配的提交都排第 1 名；从剩余提交中按同样规则选出第 2 层，依此类推。
- 解决任务数少于 7 个的最佳提交，排在上述所有提交之后，仅按解决的任务数排序。
- 相同名次视为并列，下一名次会计入前面所有人，例如：1、1、1、4……
- 只有当新提交的排名严格优于当前最佳提交时，它才会成为新的最佳提交。排名相同时，保留当前最佳提交。

### 关于排行榜提交的更多信息

- **排行榜共有 26 个任务**，编号为 1 到 26。如果在 Submit 页面指定了任务数量，则只使用前 *k* 个。
- **每轮运行在 4 小时后被终止**，从 Agent 打开第一个任务时开始计时（见第 0 部分的规则）。
- **崩溃或超时的运行仍然计入结果**，按此前已经完成的任务计算。Past submissions 页面还会显示每次提交中各任务的结果，编号为 1 到 26，包括耗时、交互轮数，以及未解决任务的简短原因：
  - *not opened*：Agent 从未请求该任务，或者在请求前本轮运行就已超时。
  - *not finished*：该任务仍处于打开状态时，运行崩溃或超时。
  - *no patch*：任务结束时补丁为空。
  - *tests did not run*：评测没有产生测试结果。
  - *import error*：无法收集测试，例如发生导入错误或语法错误。
  - *broke existing tests*：应用补丁后，原先通过的测试失败。
  - *new tests failed*：修复本应使其通过的测试仍然失败。一个任务可能同时出现最后两种原因。
- **评测过程中会检查费用。** 评分器每 2 分钟汇总一次本轮运行的累计费用。如果费用达到当天剩余预算，评测就会停止，以 `Reached the budget` 状态保存，并记录此前完成的结果。
